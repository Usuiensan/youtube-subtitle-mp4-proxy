# 字幕IDと自然な日本語を両立する翻訳方式

> 状態: 採用済み。通常経路は「意味グループ単位の完成訳＋Pythonによる決定的な再分割」とする。

## 目的と採用方針

YouTubeの字幕を日本語へ翻訳し、元字幕と日本語字幕を動画へ焼き込むシステムを運用している。現在は元字幕の各IDと時刻を保ったまま、LLMにIDごとの訳文を返させている。しかし本番で、JSONの形式は正しいのに、訳文だけが少しずつ別IDへ移動し、音声と字幕が最大約27秒ずれる障害が発生した。

実装は、次の条件を満たす翻訳・再分割方式とする。

- 元字幕のID数と時刻を維持する。
- 日本語と元字幕の対応が途中からずれない。
- 前後の文脈を使い、実際の翻訳字幕らしい自然な日本語にする。
- 文法上必要なら、各IDの日本語が言い切りでなくてもよい。
- 1 IDずつ独立して翻訳する方式には、通常時にも異常時にもフォールバックしない。
- 通常時のAPIコストと処理時間を大きく増やさない。
- 整合性を確認できない訳文を、完成動画として公開しない。

採用方式は、**文・発話単位で自然な完成訳を作り、その完成訳をPythonで元ID数へ再分割し、連結すると完成訳へ戻ることを検証する方式**である。翻訳単位、APIバッチ単位、表示単位を分離し、LLMへ字幕IDごとの対応付けを要求しない。

通常経路でLLMに完成訳と分割を同時生成させる方式は採用しない。Pythonだけでは自然な分割を選べないグループに限り、確定済みの完成訳を変更しない候補選択としてLLMを使う。1 IDずつ独立して翻訳するフォールバックは設けない。

## 対象システム

リポジトリは `youtube-subtitle-mp4-proxy`。主な処理は次のファイルにある。

| 役割 | ファイル・関数 |
|---|---|
| 意味グループ化、APIバッチ化、翻訳検証、再分割、SRT保存 | `app/translation.py` の `translate_srt_with_local_worker()`、`build_meaning_groups()`、`split_group_translation()` |
| Gemini/OpenAI向けプロンプトとStructured Output | `app/translation_worker.py` の `build_full_translation_prompt()`、`translation_group_schema()` |
| モデル・推論レベルの再試行計画 | `app/main.py` の `translation_attempt_plan()` |
| 元字幕と翻訳字幕のASS生成・動画焼き込み | `app/main.py` の `ffmpeg_dual_subtitle_args()`、`build_ass_from_srt()` |

## 障害発生時の旧実装

### 1. 元SRTをトークン量でチャンク化する

`app/translation.py` はSRTを読み、既定では推定入力が約3500トークン以内になるよう字幕をチャンク化する。文末や発話境界ではなく、トークン量が境界の主な基準になっている。

今回問題になったチャンクは、字幕ID `331`〜`439` の109件だった。

### 2. 前後の字幕を文脈として付ける

各チャンクには、直前の翻訳済み字幕と次チャンクの元字幕を最大5件ずつ渡す。前後文脈は名前や代名詞を解決する参考情報であり、出力対象には含めないようプロンプトで指示している。

### 3. LLMにIDごとの訳文をまとめて返させる

Geminiには、対象IDをすべてプロパティにしたobjectスキーマを渡す。

```json
{
  "subtitles": {
    "331": "字幕331の日本語",
    "332": "字幕332の日本語",
    "...": "...",
    "439": "字幕439の日本語"
  }
}
```

問題チャンクでは、`subtitles` objectの中に109個の必須文字列プロパティがあった。各プロパティのスキーマは単なる`STRING`であり、対応する元字幕本文はプロンプト側の一覧にだけ含まれる。

プロンプトでは、次を明示している。

- 各IDを独立して翻訳する。
- 隣接IDを結合しない。
- 隣の字幕を使って文を完成させない。
- 意味を別IDへ移動しない。
- 文の断片であっても、その境界を維持する。

### 4. 構造を検証して元時刻へ戻す

旧`validate_translations()` は主に次を検証していた。

- 必要なIDがすべて存在する。
- IDの範囲が順番どおりである。
- 欠番、重複、逆順がない。
- 訳文が空文字ではない。

検証後、各日本語を対応する元字幕の開始・終了時刻へ割り当て、翻訳SRTを保存する。ffmpeg側はその時刻を変更せず焼き込む。

### 5. 形式エラー時だけチャンクを分割する

JSON不正、出力切断、ID欠落などのエラーは、条件を満たせばチャンクを左右に分けて再翻訳する。一方、すべてのIDが文字列として返っていれば、内容が別IDの訳でも成功扱いになる。

## 本番で発生した問題

対象動画は `Otm3HChL4w8`。スペイン語字幕から日本語へ、`gemini-3.1-flash-lite`、`thinkingLevel=minimal` で翻訳した。

問題リクエストの実績は次のとおり。

| 項目 | 値 |
|---|---:|
| 対象字幕 | ID 331〜439、109件 |
| 入力トークン | 2790 |
| 出力トークン | 1974 |
| 出力上限 | 6654 |
| 終了理由 | `STOP` |
| APIエラー | なし |
| JSON構造エラー | なし |

出力上限には十分な余裕があり、`MAX_TOKENS`でもなかった。Gemini APIの生レスポンスの時点ですでに内容がずれていたため、JSONデコード、SRT保存、ffmpeg、再生側が原因ではない。

### ずれはID 355付近から累積した

最初の明確なずれは次の箇所だった。

| ID | スペイン語入力 | GeminiがそのIDへ返した日本語 |
|---:|---|---|
| 355 | `Así que me gusta quitar la manguera inferior del radiador,` | ですから、可能であればラジエーターの下側のホースを外すのが好きです。ラジエーターホースです。 |
| 356 | `si es posible. Es la manguera del radiador.` | そしてクランプを外します。 |
| 357 | `Y le voy a quitar la abrazadera.` | 時々、これらのホースは非常に固着していることがあります。 |
| 358 | `Y a veces, estas mangueras suelen estar muy atoradas.` | 私がよくやるコツは、ゴムを優しく掴んで |

ID 355の訳にID 356相当の内容まで入ったため、ID 356以降には次の字幕の訳が入り始めた。その後も、複数の元字幕断片を一つの日本語へまとめるたびに前倒し量が増えた。

- ID 355付近：およそ1件前倒し
- ID 369付近：2件以上前倒し
- ID 409付近：7件前後前倒し
- ID 420付近：10件前倒し
- ID 430〜439：残りの訳文がなくなり、すべて「完了」

ID 420の表示時刻は18分20.015秒だったが、そこには本来27.104秒後のID 430相当の内容が入った。このため、視聴時には字幕が音声より大きく先行した。

### 元字幕には同規模のずれがなかった

同じ動画の手動スペイン語字幕と英語自動字幕の開始時刻を比較したところ、最寄り開始時刻との差は中央値0.461秒、95パーセンタイル1.106秒、最大1.760秒だった。分割粒度による小さな差はあるが、今回の27秒級のずれを説明できるものではなかった。

## 原因の見立て

Geminiは、109個のIDを独立した翻訳単位として厳密に処理するより、字幕列を連続した文章として自然に訳すことを優先したと考えられる。元字幕が文の途中で細かく分割されていたため、複数IDの内容を一つの日本語へ統合し、その後の訳文を残りのキーへ順番に入れた。Structured Outputは109個の文字列キーが存在することを保証したが、それぞれの訳文が対応する入力IDだけに由来することまでは保証しなかった。

大きなチャンクだけが原因とは断定できない。同じモデルで106件、111件、115件のチャンクが正常に完了した例もある。現時点では、次の条件が重なった確率的な失敗と見ている。

- 文途中で分割された字幕が多い。
- 109件の対応関係を一度に維持する必要がある。
- 各スキーマプロパティには元字幕本文との意味的な結び付きがない。
- 軽量モデルを最小推論で使用している。
- 自然な文章を作る目的と、ID境界を守る目的が競合している。

## 確定している要件

### IDと時刻

- 出力は元字幕と同じID数を持つ。
- 各出力は元IDの開始・終了時刻へ割り当てる。
- ある文・発話の意味を、その範囲外のIDへ移動しない。

### 翻訳品質

- 翻訳時は前後文脈を利用する。
- 日本語の語順へ自然に並べ替えてよい。
- 各IDを無理に文として完結させない。
- 連続表示したときに自然なら、「〜ので」「〜なら」「〜して」「〜の」のような継続形を許容する。
- 字幕用途に適した簡潔な日本語にする。

### フォールバック

- 1 IDずつ独立して翻訳する方式は使わない。
- 異常時も文・発話単位の文脈を維持する。
- 再試行して整合性を確認できなければ、壊れた動画を完成扱いにせずジョブを失敗させる。

## 採用した設計

### 文・発話単位で完成訳を作り、元ID数へ再分割する

翻訳単位と表示単位を分離する。

1. 元字幕を句読点、発話間隔、話者変更などから文・発話グループへまとめる。
2. グループ全体を自然な日本語へ翻訳する。
3. 完成した日本語を、元ID数と各表示時間に合わせて分割する。
4. 分割結果を元IDへ順番に割り当てる。
5. 分割結果を連結すると完成訳へ戻ることを検証する。

例：

```text
元ID 355: そういうわけで私はラジエーター下部のホースを外すのが好きです、
元ID 356: 可能であれば。それはラジエーターホースです。

完成訳: 外せる場合はラジエーターの下側ホースを外します

ID 355: 外せる場合は ラジエーターの
ID 356: 下側ホースを外します
```

各断片は単独では完全文でなくても、連続表示で自然に読めればよい。

### 最低限の機械検証

- `segments`の件数が元ID数と一致する。
- すべての要素が文字列である。
- 空文字やメタ表現による穴埋めがない。
- 正規化後の`segments`連結結果が、完成訳と一致する。
- 原文にある数字、URL、型番を文・発話グループ内で順序どおり保持する。数詞や不定冠詞を自然な日本語で数字表記にする場合は、原文の数字を欠落・変更していなければ許容する。
- 同じ短文が異常に連続していない。
- 各表示時間に対して文字数が過大でない。
- 最大行数など、現在の字幕表示制約を満たす。

異常時は同じ文脈を保ったまま、グループ縮小、推論レベル引き上げ、高精度モデルへの切り替えを行う。すべて失敗した場合はジョブを失敗扱いにする。

## 検討時に比較した案とpros / cons

| 案 | 概要 | Pros | Cons・リスク | 現時点の評価 |
|---|---|---|---|---|
| A. 現行の大チャンク＋ID-keyed object | 100件前後のIDを一度に翻訳し、各IDをobjectのキーにする | API呼び出しが少ない。実装済み。構造上の欠番を検出しやすい | 文断片の統合で意味対応が累積的にずれる。JSONが正しくても壊れた字幕を受理する | 廃止候補 |
| B. 1 IDずつ独立翻訳 | 1件ずつ前後文脈付きで翻訳する | IDの構造対応は最も単純 | API回数、コスト、処理時間が大幅に増える。日本語の語順変更が難しく不自然。フォールバックとしても許容不可 | 不採用 |
| C. 小さな文グループを直接ID別に翻訳 | 2〜6件程度の文グループごとに、各IDの訳を直接返す | 現行方式からの変更が比較的小さい。文脈を維持できる。失敗範囲が局所化する | 小規模でもID間の意味移動は起こり得る。完成訳全体がないため、欠落・追加の検証が弱い | 改善案だが単独では不十分 |
| D. 完成訳＋分割を1回で返す | 文グループ全体の`translation`と、同数の`segments`を同一レスポンスで返す | API呼び出し1回。自然さとID数を両立しやすい。連結一致を検証できる | モデルが完成訳と分割を同時に考える。両方が同じ誤訳を共有する可能性がある | 通常経路には不採用 |
| E. 完成訳と分割を2回に分ける | 1回目で自然な完成訳、2回目で完成訳を指定数へ分割する | 翻訳と分割の責務が明確。分割工程は元文を再翻訳せず、内容保存を強く検証できる | API呼び出しが約2倍。分割だけの呼び出しにも遅延と料金がかかる | Python候補からの選択に限定して異常時のみ採用 |
| F. 完成訳を決定的アルゴリズムで分割 | 完成訳を句読点、文節候補、表示時間、文字数からコードで分割する | 分割の再現性が高い。2回目のLLM呼び出しが不要。内容の欠落・追加がない | 日本語の文節判定が難しい。形態素解析や複雑なスコアリングを入れると過剰設計になりやすい | 単純な規則で十分か要検証 |
| G. 高精度モデルへ変更するだけ | チャンク・出力形式は維持し、推論レベルやモデルだけ上げる | 実装変更が最小 | 構造上の弱点が残る。高精度モデルでも意味対応の保証はない。コスト増 | 補助策であり根本解決ではない |
| H. 対象言語側でID・時刻も再生成する | 日本語字幕に合わせてイベント数と時刻を作り直す | 字幕品質を最適化しやすい。言語間の語順差を最も自然に扱える | 元ID保持の要件と衝突する。音声アラインメントが別途必要。変更範囲が大きい | 今回の範囲外 |

## 検討時のDとEの比較

### D：1回のレスポンスで完成訳と分割を返す

想定スキーマ：

```json
{
  "translation": "外せる場合はラジエーターの下側ホースを外します",
  "segments": [
    "外せる場合は ラジエーターの",
    "下側ホースを外します"
  ]
}
```

`segments`には`minItems`と`maxItems`で元ID数を指定する。ID自体はモデルに出力させず、アプリ側が配列順に割り当てる。

利点は、通常時のAPI呼び出しが1回で済み、完成訳と分割の連結一致を検証できること。欠点は、モデルが翻訳と分割を同時に行うため、完成訳そのものが分割都合に引っ張られる可能性があること。

### E：完成訳と分割を別リクエストにする

1回目は文・発話全体の自然な字幕訳だけを作る。2回目には元文を翻訳させず、確定済みの日本語と各IDの表示時間だけを渡し、文字列を指定数へ分割させる。

利点は、2回目の結果を連結して1回目の完成訳と完全一致させられること。分割工程で意味を増減できない。欠点は、すべての文グループでAPI呼び出しが2回になること。

最終的にはDを通常経路にせず、完成訳をPythonで再分割する。分割が難しい場合だけ、完成訳を一切変更できない複数候補からLLMに選択させる。

## 文・発話グループの作り方

グループが小さすぎると日本語の語順変更が難しくなり、大きすぎると対応ずれと再試行コストが増える。候補となる境界は次のとおり。

- 文末記号、疑問符、感嘆符の後
- 明確な無音区間の後
- 話者が変わる位置
- 場面転換
- 一定以上の時間差
- 最大ID数または最大表示時間に達した位置

文末記号がないYouTube字幕や、自動字幕に近い断片では、句読点だけでは正しくまとめられない可能性がある。最初から高度な文境界モデルを追加するより、単純な規則と小さな上限で十分かを実データで検証したい。

## 日本語の再分割方針

分割位置は、次の順で評価する想定である。

1. 意味・文節の境界
2. 読点や接続部
3. 助詞や接続助詞の後
4. 各IDの表示時間に対する文字数の均衡
5. 1行あたりの文字数と最大2行の制約

名詞と強い修飾語、動詞と助動詞、固有名詞の途中などでは切らない。各IDを無理に言い切りへ変えず、連続表示したときに自然な形を優先する。

例：

```text
自然:
355: 外せる場合は ラジエーターの
356: 下側ホースを外します

自然:
359: ゴムを軽くつかみ
360: 左右に回して固着をはがします

避けたい:
359: ゴムを軽くつかみます
360: そして左右に回します。そして固着をはがします
```

## 再試行案

1 IDずつの独立翻訳は使わず、次の順に再試行する。

| 段階 | 翻訳対象 | 文脈 | 変更点 |
|---|---|---|---|
| 通常 | 複数の意味グループ | 前後あり | グループ完成訳を生成し、Pythonで再分割する |
| 応答不正 | 不正な同じグループだけ | 前後あり | 正常グループを保持して再翻訳する |
| 分割困難 | 翻訳は行わない | 元文・時刻あり | 完成訳を変えないPython候補から選択する |
| API全体失敗 | 同じAPIバッチ | 前後あり | 既存の推論レベル・モデル再試行計画を使う |
| 全失敗 | 採用しない | — | ジョブを失敗扱いにする |

元から1件だけで意味が完結する字幕は、結果的に1 IDのグループになり得る。その場合も前後文脈は渡す。禁止したいのは、異常時に全文を機械的に1 IDずつ分解して独立翻訳するフォールバックである。

## 検討時にChatGPTと議論した論点

1. 有力案Dの「完成訳＋segmentsを同時生成し、連結一致を検証する」方式で、意味対応ずれを十分に抑えられるか。
2. 通常はD、検証失敗時だけEへ移る折衷案は、複雑さに対して十分な効果があるか。
3. 文・発話グループを作る最小限の規則は何か。句読点、時間差、最大ID数の三つだけで始められるか。
4. 日本語の再分割をLLMへ任せる場合、どの入力情報が必要か。各IDの開始時刻、終了時刻、継続時間、文字数目標のうち、何を渡すべきか。
5. `segments`の各要素を空文字禁止にすべきか。日本語が短い場合、意味のない穴埋めを避けながら元ID数を維持するにはどうするか。
6. 連結一致、数字保存、反復検出、表示速度以外に、低コストで決定的に検証できる条件はあるか。
7. 高精度モデルへの切り替え条件を、どの検証失敗に限定すべきか。
8. 元IDの時刻を完全維持する要件と、日本語の読みやすさが衝突した場合、どちらをどの範囲まで優先すべきか。
9. 今回の109件object方式から移行する際、最小実装で済む設計はD、E、または別案のどれか。
10. この設計で見落としている、字幕特有の障害パターンはあるか。
